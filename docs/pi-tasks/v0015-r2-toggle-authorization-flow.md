# V0015-R2：手形仅标志，开关为唯一权限操作入口

用户最新明确纠正：“不应该是点击哪个手吧，手只是标志，点击的还是开关，只是跳出授权窗口？…然后你验收下”。此指令覆盖旧补充“点击手、禁用开关”的交互，手形的样式/位置保持Alcove，不能再拿旧归档blocked禁用逻辑抵触用户澄清。先读AGENTS和docs/verification/independent-v0015-r1/decision.md。

## 必须实现的交互

- hand.raised.slash.fill仅为状态标志，不再是Button/可点击焦点入口；不要给手形绑定授权动作。位置/颜色/大小沿用现有样式。
- 真正点击的是功能开关。未授权也能点击“尝试开启”，不能disabled(blocked)挡住；在SettingsView的开关Binding或最小现有适配层拦截开启意图，调用该功能真正的权限路径。
- 未决定/unknown：用户点开关才请求系统授权/执行必要的明确权限尝试；没有系统可用弹窗时如实引导对应设置，不能假装成功。拒绝/受限：按系统允许的方式引导设置，不尝试循环弹窗/绕过拒绝。
- 成功后该次开启意图完成：标志消失，功能开关变开启并开始对应功能；不能仅授权成功但还要用户再点一次开关。拒绝/取消/失败则保持关闭并如实反馈。
- 用户取消开启意图或明确关闭后，过期权限回调不得突然开启功能；连续点击/授权进行中不得创建多个请求，按当前意图一次完成。返回系统设置/应用激活刷新真实状态，只在仍有效的本次开启意图下自动完成，不把外部授权变化当开启全部功能。
- 已开启时“关闭”始终可点，不因权限unknown/被撤销而把关闭入口禁用；关闭停止实际检测/音频，不撤销系统权限。普通无需权限的设置维持原操作。

## 当前源码问题及保持项

当前SettingsControls SettingsToggleRow是手形Button+Toggle.disabled(blocked)，SettingsView三个权限行将request绑定onAccessory；需改成开关入口。当前SettingsView.onChange只在失去权限时关闭，没有pending开启成功联动。

AppPermissions.requestBluetoothAccess硬编码0.8s后认为未授权并弹message，系统对话框可能仍等待用户操作；不得将0.8s未响应判作拒绝或自动开系统设置。应按可证实的权限结果/应用激活状态收尾，避免重复弹窗/提示风暴。IOBluetooth明确权限请求是否会触发系统弹窗仍须以公开API/实机证据区分；不绕过新授权或更换成熟设备检测实现。系统音频没有可靠preflight时保持unknown而非伪造denied；已有音频授权/已开启波形不可被假unknown禁用关闭。

蓝牙检测、实时波形及登录项requiresApproval分别处理正确系统能力；不新建权限中心/新页面，不引入无关架构。设备页仅总开关、固定自动3D+既有图标回退；R1生命周期/声音停止及185→194测试已接受子集保持，不改原音乐/歌词/多屏。

## 验证与交付

必须验证实际开关路由，不能只直接调用AppPermissions.request方法就称交互通过。使用注入权限/source/sound/系统设置spy，覆盖点击关闭开关→请求一次→授予→开关真开启/手形消失、拒绝或取消保持off、等待中取消/迟到回调、denied设置引导/返回、已开权限unknown仍可关闭。无权限状态截图/AX应显示手形为图像或状态文本，开关仍可操作，不是手形按钮。授权前不写用户真实权限/登录项，不实播/连接设备。
