# 桌面静置 CPU 优化：第一批

用户最新授权：开始实施，但先解决解锁后的桌面场景，完成并验收后再处理锁屏。功能和体验不能退化，静置与播放/交互分别测量。分支 codex/idle-cpu-optimization；遵守 AGENTS.md，使用现有会话，不改模型。

## 已有证据及局限

- 安装版 1.0.3 build26 的一次解锁桌面测量：61 秒增加 2.40 CPU 秒，约 3.93% 单核；主进程 RSS 约136 MiB，媒体实际播放状态未记录。这不是严格受控基线。
- Controllers.swift 的0.25秒定时器有快照就调用 setElapsed，暂停也发布同值；AppModel.elapsed 为 Published，多处 View 观察整个模型。
- ConnectivityController.applySnapshot 无条件赋值 devices/audioOutput；相同设备快照也触发订阅者。
- 短 sample 仅捕获调用路径，包含阻塞等待，禁止换算模块CPU份额或承诺节省百分点。

## 本批实施范围

1. 暂停/进度未变时减少无效进度发布。先核对时间锚语义，再做最小改动。播放可见期间维持既有0.25秒更新及歌词30Hz时间轴；不降低动画帧率。保留恢复播放、seek、切歌、倍速变化、媒体流失效重连和命令失败回滚语义。不能简单在全局setElapsed加guard而忽略时间锚。
2. 设备展示数据未变时避免重复发布devices/audioOutput；连接识别、待连接状态、低电量判断、断开清理、迟到快照、提示生命周期仍照常处理，不能提前返回跳过业务逻辑。轮询频率保持原样。
3. 优先做以上两项。若无法证明不改变功能或体验，说明风险并停下，不扩大范围。暂不修改锁屏文件、玻璃、锁屏歌词路径、窗口扫描频率、音频查询频率或菜单栏刷新周期；不做UI重构。

- 跑改动模块及必要相邻测试，记录命令、结果、改动原因和未验项到 docs/reports/desktop-idle-cpu-first-pass.md。

- 不擅自控制真实媒体、设备或权限，不提交推送、不安装替换运行版。构建测试可以，暂不正式打包递增版本。
