## 用户新版实测（未经独立控制条件复测）

- 无播放静置约1% CPU。
- 点击日历约10%，停止操作回到1%。
- 刘海存在浮动或播放时持续约10%。
- 切歌约20%，完成后回到10%。

本批优先持续播放/浮动的约10%，不优先处理短暂日历/切歌峰值，不宣称具体降幅或强行追求播放态1%。媒体状态、歌词可见性和浮动含义需通过现有证据区分，不把所有“无操作”都当成无动画静置。

## 调查重点与实施约束

1. 阅读 CompactLyricsView 的30Hz时间轴：检查无歌词/空时间轴时是否存在无用刷新。只有确认输出静态且不漏掉未来更新，才暂停/避开时间轴；歌词加载完成须立即恢复。已有时间轴的前奏/句间空白仍可能需要进入下一句，不能仅因当前line为nil永久停时钟。保留逐字高亮、滚动、行切换、暂停保留行和尺寸。
2. 阅读 Controllers/AppModel、NotchView、MusicPlayerContent、MediaProgressView 的4Hz进度发布与观察边界。若证据支持无关视图重复计算，再做最小隔离/缓存/去重。不直接全局降低播放进度频率或歌词帧率，不泛化重构AppModel；时间锚、恢复/seek/切歌/倍速/命令失败/重连语义必须保留。
3. 阅读 CompactPlaybackControl、WaveformClock、MarqueeLabel 和 WindowCoordinator，确认不可见、收起、窗口orderOut或视图移除时是否还保留动画工作。window != nil 不等于屏幕可见，suspended/active与真实可见性需核实；可见时保留现有波形/跑马灯动画节奏。不要仅凭代码存在定时器就断言CPU占比。
4. 不改锁屏专属文件/玻璃/锁屏UI，不改日历/菜单栏刷新/设备或音频轮询频率。本批若涉及共享歌词或波形组件，须覆盖共享行为回归，但不得顺势扩成锁屏专项。

先定位再选改动：不是要求三项全改。若没有足够证据或无法保证体验，写明未解决项，不盲目改动。sample包含等待栈，不能用样本数推CPU份额或把App CPU归给WindowServer；静态分析、隔离计数、真实CPU结果分别报告。
