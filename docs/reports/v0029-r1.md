
No Convoy app, browser host, extension, Sparkle, updater, Convoy UI or nested `.git`
is included. The top-level `Package.swift` uses `.package(path: "Vendor/Convoy")` and
links only the **DownloadEngine** product. `Package.resolved` has only swift-log
1.16.2; there is no remote Convoy or Sparkle pin. The signed candidate links
DownloadEngine symbols and has **no Sparkle link**.

The patch is limited to ownership, configuration and lifecycle boundaries:

| File | Change |
|---|---|
| `Models/DownloadEnvironment.swift` (new) | Explicit persistence/scratch/defaults/settings/default-download/helper/trash ownership; upstream default is kept only for compatibility. |
| `Models/Settings.swift` | Injected `UserDefaults`; `@AppStorage`/standard-only storage removed; `restoreDefaults` acts on the injected suite. |
| `Models/DownloadTask.swift` | Weak owning `DownloadManager`; explicit scratch container; late-identity/duplicate/conflict callbacks go through the owning manager; YouTube/helper paths gated; settings read through the owning manager. |
| `Models/DownloadSegment.swift` | Scratch-container parameter. |
| `Services/DownloadManager.swift` | `init(environment:)`; isolated list lock/persistence/scratch; task ownership attachment; environment trash hook; launch temp measurement opt-in; explicit helper gate. |
| `Services/StreamDownloader.swift` | Scratch-container parameter. |

`TaskScratchDirectory.swift` and `TemporaryStorage.swift` were inspected and are
unchanged; their container argument is supplied by the manager/task flow. Download
segment splitting, pause/resume, retry, merge, rename/duplicate conflict and delete
semantics were not redesigned.

`DownloadManager.shared` and `AppSettings.shared` remain as upstream-compatible
defaults, but **Valora never references either**. Valora's explicit production
environment, when a future UI calls it, is:

```text
~/Library/Application Support/Valora/Downloads/downloads.json
~/Library/Caches/Valora/Downloads/
suite com.wangqing.valora.downloads
allowExternalHelpers = false
measureTemporaryStorageAtLaunch = false
```

No manager or download service is constructed in `AppDelegate` or `main`; app launch
does not load, recover or measure downloads. The real `DownloadEngineService` is an
explicit adapter and is not wired into the current placeholder Downloads page.

## 2. Real engine verification (not the fake service)

Evidence: `docs/verification/v0029-r1/logs/test-isolation-real.log`.

`Tests/ValoraTests/DownloadEngineIsolationTests.swift` uses a local Python HTTP
server (`Tests/ValoraTests/Fixtures/range_http_server.py`) with Range support and a
0.5 s delayed body, plus temporary roots only.

1. **Real multi-segment Range download + pause/resume**
   - 20 MiB source; observed `activeSegments > 0` and `segments.count > 1`.
   - Pause reached `.paused`; resume reached `.completed`.
   - Completed file SHA256 equals the source SHA256.
   - Duplicate re-enqueue produced a pending conflict and did not modify the file.
   - Delete with `moveFilesToTrash: false` removed the record while retaining the
     completed file.
2. **A/B roots, cancellation and failure**
   - A and B have distinct persistence, scratch, defaults suites and output roots.
   - A wrote/cancelled its task without touching B's sentinel (`b-only`) or B's item
     list; no scratch entry containing the cancelled task ID remained.
   - A `file:///valora-not-a-download` attempt reached `.failed`; `activeCount == 0`.
3. **Explicit trash**
   - With the QA environment's injected trash closure, `delete(..., true)` moved the
     completed file into the test root's `trash/`; the original path disappeared.
   - The production `FileManager.trashItem` path is **not exercised by tests**.
4. **Restart, list lock, unreadable record**
   - Completed task saved, service released and recreated in the same environment:
     the completed record reloaded.
   - A second manager at the same list reported `ownsDownloadList == false`.
   - An unreadable list was moved to `downloads-unreadable-*` inside that test root.

The real service was not replaced with `FakeDownloadService`. No real user Convoy
directory, real Downloads content or real Trash was read or modified.

## 4. Static audit and remaining boundaries

Evidence: `docs/verification/v0029-r1/source-audit.log`.

- **Valora-reachable download paths:** only `Sources/Valora/DownloadEngineAdapter.swift`.
  It imports the engine, defines `DownloadEngineService(environment:)`, and is not
  constructed by the app entry point. There is no `DownloadManager.shared` or
  `AppSettings.shared` use in Valora.
- **Upstream singleton declarations:** `DownloadManager.shared`, `AppSettings.shared`,
  `HelperAutoUpdate.shared` and YouTube singletons remain in the vendored upstream
  source for compatibility. They are not referenced by Valora's app entry or current
  UI.
- **Explicit paths:** persistence, scratch, temporary measurement, task callbacks and
  trash all receive the manager environment. `DownloadTask` owns only a `weak`
  manager; no manager↔task retain cycle was introduced.
- **External-helper gates:** `allowExternalHelpers = false` guards YouTube enqueue,
  resolution, pause/cancel and late auto-resolution. `DownloadTask` passes the
  manager's settings for cookie-related settings, but no cookie read occurs on the
  direct HTTP path.
- **Static-only, not executed:** `HelperAutoUpdate`, `YouTubeHelperInstaller`,
  `HelperInstallProgress`, `BrowserIntegration`, and the full YouTube helper/cookie
  machinery. Their `.standard`/temporary-directory references and auto-installer/
  browser code were not exercised by this task and are not claimed isolated.
- **Default fallbacks:** `AppSettings(defaults: .standard)`,
  `AppSettings.shared`, `DownloadManager.shared`, and helper temporary-directory
  defaults remain for upstream compatibility. Valora constructs neither shared
  object and passes its own roots/defaults for manager flows.
- **Trash production path:** only the injected QA closure was tested. The real
  `FileManager.trashItem` implementation remains the production default for a future
  UI and must be tested separately with user approval.
- No real external resource download, helper install, browser integration, cookie
  read, permission write, media/device/account/calendar write or user Downloads
  access was performed.
- No upstream fork, `git commit`/push, `.build/checkouts` modification, install,
  publication or model-history change was made.

## 5. Rebuild and upgrade verification

```sh
# clean upstream checkout at the pinned revision
python3 scripts/verify_convoy_vendor.py --upstream /tmp/convoy-v0029

# local package and Valora
swift build --package-path Vendor/Convoy
swift build
swift test --filter DownloadEngineIsolationTests
swift test
./scripts/build.sh --output-dir /private/tmp/valora-v0029-r1-candidate
```

The verifier fails on a wrong upstream revision, changed upstream content, missing
local file or forbidden app/Sparkle/host/extension directories. It compares the
upstream and local hashes in `SOURCE-MANIFEST.json`; it does not silently fall back to
a fuzzy patch. A revision or source-hash mismatch is an upgrade failure, not an
automatic replacement.

The reviewable patch is `Vendor/Convoy/patches/V0029-R1-COMPAT.patch`; the same patch,
manifest, license, notices and package files are copied under
`docs/verification/v0029-r1/source/`.
